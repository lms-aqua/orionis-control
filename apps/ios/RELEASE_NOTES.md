Orionis Control 1.4.0 adds seven more camera sources: Reolink, Dahua (which also covers Amcrest), Hikvision, Axis, Foscam, VIVOTEK, and a generic ONVIF source for everything else. All of them talk to the camera on your own network — its own login, nothing sent to a vendor cloud — and give you snapshots and live view. The ONVIF source is the catch-all: point it at any standards-compliant camera and it asks the camera itself for its stream and snapshot URLs, so brands without a dedicated source still work without you hunting down the right path. As with the other local sources, motion events, saved recordings and pan-tilt are left off rather than half-wired — each source says what it does instead of showing tabs that fail. These are verified by tests and against the vendors' documented interfaces; the live connection to your own camera is the one thing only you can confirm.

Orionis Control 1.3.0 adds Scrypted as a camera source. If you run a Scrypted server, add it once with its address and your login, and its cameras show up on the wall alongside everything else — with snapshots, and live view through the same path the other sources use. Scrypted talks its own protocol rather than a plain web API, so this connects the way Scrypted's own apps do. Events, recordings and pan-tilt controls aren't wired up yet; the source says so plainly instead of showing empty tabs.

Orionis Control 1.2.0 stops Blink from texting you a code every time. Adding a Blink source used to set its helper up the moment you tapped Add — before you had signed in — so the helper met Blink as a stranger with only an email and password and got mailed a fresh verification code on every start, forever. Now the order is the other way round: you add the source, sign in once with the code Blink sends, and only then does Orionis stand the helper up and hand it the verified session. One code, at the start, in the app — not a stream of them at a console nobody is watching. Sources that do not sign in this way (Wyze, a plain RTSP bridge) are unchanged and still set up as soon as you add them.

Orionis Control 1.1.0 stops asking you to be the plumber. Adding a Blink camera used to mean typing two container addresses before the form would accept anything — and the addresses it suggested named a container that does not exist on most installs, so the first thing you met was a screen that refused to save. Blink now asks for an email and a password. Everything underneath is Orionis's problem: when a source needs a helper service, the app offers to start one, the server brings it up from a template that ships with the release, and the connection fills in its own addresses when it is ready. The verification code Blink sends arrives in the app, where you can type it, instead of in a terminal on the server.

The same applies to Wyze, and to any RTSP source that needs a discovery service. Sources that are already systems you own — Frigate, UniFi Protect, a Tapo camera, Nest — are unchanged: you point at them, because there is nothing to start. Where a helper is optional the fields are still there, tucked into an advanced section rather than blocking the form, and a connection saved without one signs in and says live view needs a bridge rather than failing in a way that names software you have never heard of.

This release also fixes a bug that reached well outside the app. Opening a recording could silence the microphone for whatever else was running — a call, a screen share — and it stayed silenced until Orionis was force-quit. The app was claiming the device's audio exclusively and never giving it back: the live viewer set an output-only audio mode and left it set, the recordings player then activated it without ever releasing it, and nothing put things back. Camera audio now mixes with everything else on the phone instead of taking it over, and the session is handed back the moment playback stops, so other apps are told they can resume.

Cameras that are recording now say so. The home screen's recording count and the badge on each camera only ever lit up for a source that positively reports it, and the recorder behind most setups could not prove a camera was live — so footage was being written while the app showed nothing recording. The gateway now reads that from the recorder itself: a camera with fresh footage reads as recording, one whose footage has stopped reads as not, and only a recorder it genuinely cannot reach reads as unknown.

One thing worth knowing: that audio fix is verified by tests and by inspection, not on hardware. If a call or a screen share still loses its microphone when you open a recording, that is worth reporting rather than working around.
